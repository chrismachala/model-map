Context, retrieval and memory

The model sees only what the harness puts in front of it this step. Choosing that (context engineering), fetching the right passage (retrieval), and keeping track of what's true now (state and memory) are three different jobs, and most agent failures come from getting one of them wrong.

Kind: LLM-based agent.
Week: 6, Part III second half (slides 30 to 37).
Book: not in Wooldridge. Optional: Anthropic, Effective context engineering for AI agents (2025) and Introducing contextual retrieval (2024); Lewis et al. 2020 (RAG); Sumers et al. 2024 (CoALA).
Techniques on this page: context engineering and the budget game, retrieval-augmented generation, keyword vs vector search and cosine similarity, state reconciliation, kinds of memory, compaction for long runs.

The problem it solves

A context window is finite, and even when it’s big, filling it costs money, time and the model’s attention. Meanwhile the useful information lives in four different places: the model’s weights (general knowledge, not current), documents (the baggage policy), live systems (today’s fare) and the agent’s own records (what it did earlier). Each needs a different way in. And a fact being somewhere in the context doesn’t make it current.

Words you’ll hear

Word Plain meaning
context engineering deliberately choosing what goes into the model’s context for this step
RAG retrieval-augmented generation: fetch relevant passages, put them in the context, then generate
chunk a piece of a document stored in the index
sparse / keyword search score passages by shared words; rare words count more (e.g. BM25)
dense / vector search embed query and passages as vectors; return the nearest
embedding \(e(\cdot)\) a vector of numbers that captures meaning; similar texts get nearby vectors
cosine similarity \(\dfrac{e(q) \cdot e(d)}{\lVert e(q)\rVert \lVert e(d)\rVert}\): the angle between two vectors, 1 = same direction
hybrid search combine keyword and vector results
state reconciliation the harness records which fact is current, with source and time, and marks old ones superseded
working state \(m_t\) progress, constraints, current facts, pending steps
episodic / semantic / procedural memory past events / stored facts / how to do things

Technique 1: context engineering (the budget game)

Problem it solves: the model can’t use what it isn’t shown, and drowns in what it doesn’t need (slides 30 to 31).

The passenger asks “Is cabin luggage included on #517?” Budget 8,000 tokens, 1,000 kept free for the answer, so 7,000 usable.

One good answer: items 1 to 3, 5, 8, 11, 12, 14 to 16 = 6,140 tokens.

Mechanism Take Not
select 5: cabin-baggage excerpt (700) 4: the whole 40-page policy (38,000)
filter 8: three flights, fare class and price (500) 7: all 25 flights as raw JSON (11,500)
summarise 11: summary of last week (400) 10: last week’s full transcript (14,000)
disclose progressively 14: skill name + description (90) 13: full skill instructions (3,800)
keep structured state 15: progress notes (350)
prune history 16: this session, raw tool output cleared (1,600)

Plus the essentials: 1 system prompt (900), 2 tool schemas (1,200), 3 the request (150), 12 passenger profile (250). Item 6 (change fees) and 9 (price history) aren’t needed for a baggage question.

In practice much selection is just in time: the agent keeps references and fetches passages or skill text through tools when it needs them. The model sees only what the builder puts into \(c_t\).

Technique 2: retrieval and RAG

Problem it solves: each kind of knowledge has its proper access route (slide 32).

Source Use it for
LLM parameters general language and task knowledge; not a current, authoritative database
indexed documents retrieve relevant passages on demand (baggage policy): RAG
live systems query authoritative services (fares, availability): API tools

RAG pipeline: in advance, documents → chunks → index. At question time: retriever searches the index → passages → build context → LLM → answer with sources and citations.

Sources support checking, but retrieval doesn’t guarantee correctness. And a fixed retrieve-then-generate pipeline is a workflow, not necessarily an agent.

Technique 3: keyword vs vector search

Problem it solves: finding passages by exact terms vs by meaning (slides 33 to 34).

  • Keyword (sparse): the index records which passages contain which words; more query words matched = higher score, rare words count more (BM25). “pet fee” finds passages with pet and fee.
  • Vector (dense): an embedding model maps query and passages to vectors trained so similar meanings are close; return the nearest by cosine similarity. “bringing my cat” finds “pets in the cabin”.

Slide 34. P1: “Cabin baggage: one item up to 8 kg is included on all fares.” P2: “Fare rule Y-2: changes permitted up to 24 hours before departure for a fee.” P3: “Fare rule Y-3: changes not permitted after booking.”

Keyword Vector
Q1 “What is the carry-on allowance?” misses P1: no words in common finds P1: “carry-on” ≈ “cabin baggage”
Q2 “Can I change a ticket booked under Y-2?” ranks P2 first: “Y-2” is a rare exact match finds P2 and P3 but can’t tell Y-2 from Y-3

So production systems use hybrid search.

Cosine similarity by hand. \(e(q) = (1, 2, 2)\), \(e(d_1) = (2, 1, 2)\), \(e(d_2) = (0, 0, 3)\). \(\lVert e(q)\rVert = 3\). \(q \cdot d_1 = 2 + 2 + 4 = 8\), \(\lVert d_1\rVert = 3\), cosine \(= 8/9 = 0.889\). \(q \cdot d_2 = 6\), \(\lVert d_2\rVert = 3\), cosine \(= 6/9 = 0.667\). Retrieve \(d_1\) first.

Technique 4: state reconciliation

Problem it solves: two numbers for the same thing in the context, and nothing says which is current (slide 35).

Step 2’s search said #441 costs $490; step 12’s check_fare(441) said $560. The passenger asks “how much was #441 again?” Poll answer: C, it depends: usually $560, but not guaranteed. Both are just text.

The harness fixes it: store the current fact (#441 = $560, with source and time), keep $490 labelled superseded, recompute progress (#441 now breaks the budget), and put the reconciled fact into the next context. Retrieving a record is not the same as establishing that it is current or correct.

Technique 5: context, state and memory

Problem it solves: the words get used loosely; they mean different things (slide 36).

Element What it provides
model context \(c_t\) the tokens the LLM sees now
working state \(m_t\) progress, constraints, current facts, pending steps
episodic memory records of past interactions, actions and outcomes
semantic memory stored facts, retrieved on demand
procedural memory how to do things: skills, stored procedures (and, implicitly, the weights)
RAG knowledge base searchable documents; not necessarily memories of this agent

A memory system writes, stores, retrieves and updates. Typical failures: wrong item retrieved, stale entries, contradictions, constraints omitted. (The terms come from cognitive psychology via CoALA; practice often just says short-term vs long-term.)

Classify. “Last Tuesday the passenger rejected a red-eye” → episodic. “The passenger is a gold frequent flyer” → semantic. The flight-comparison skill → procedural. The 40-page baggage policy in a vector index → RAG knowledge base. “Searched SFO–NYC; #517 checked at $475; still to do: confirm baggage” → working state.

Technique 6: long runs and compaction

Problem it solves: the context grows every step and the model re-reads all of it every step (slide 37).

Remedies: compaction (history → summary + state), structured state, prompt caching, sub-agents with clean contexts. Checkpoints and files carry multi-session work: the context can be rebuilt from persistent state.

Compaction is exactly what broke run 1 in the failure autopsy: the summary kept the old $490 and dropped the newer $560 quote. Compaction must preserve reconciled state, not just whatever text happened to survive.
