LLM agents: the loop and the harness

An LLM only writes text. What turns it into an agent is the code around it, the harness: it builds what the model sees, checks every tool request, runs the allowed ones, feeds back the results and decides when to stop. Only one line of that loop is learned.

Kind: LLM-based agent.
Week: 6, Parts I and II (slides 1 to 20), plus the failure autopsy (slides 44 to 48).
Book: not in Wooldridge. The slides cite Anthropic, Building Effective Agents (2024), and Raschka, Components of a coding agent.
Techniques on this page: workflow vs agent, the agent loop, the harness as six components, the formal loop, from output to action, the minimal harness in code, the failure autopsy.

The problem it solves

The airline scenario (slide 3). The passenger asks: find a flight SFO → New York on 18 April, after 10:00, at most $500. Do not book yet. A bare LLM replies: “Coastal Air CA 1523 leaves at 11:15 and costs $389. Shall I book it?”

Two things are wrong:

  1. It fits every constraint and sounds right, but nothing was checked: no search, no fare quote. The flight may not exist.
  2. It offers to book: an action it can’t perform, and one the passenger ruled out.

Week 5 ended with “an LLM is not yet an agent”. Week 6 adds, one component at a time, what lets it observe, act and keep track. The answer to slide 4’s warm-up (“where does a good agent’s competence come from?”) is D: the pretrained model, the engineering around it, and the tools and data, jointly.

Words you’ll hear

Word Plain meaning
workflow a program fixes the path: which steps run, in what order, where the model is called
agent the model’s output helps choose the next step or tool, based on what it just observed
augmented LLM an LLM plus retrieval, tools and memory: a building block for both workflows and agents
harness (scaffold, agent runtime) all the code around the model: context building, model calls, tool dispatch, state, limits, stopping, recovery
tool call a structured request the model writes, e.g. check_fare(flight_id="441"); the harness decides whether to run it
observation what comes back: a tool result, an error, a user reply
\(c_t\), \(u_t\), \(a_t\), \(o_{t+1}\), \(m_t\) context, model output, accepted action, observation, runtime state
step limit the maximum number of loop iterations before the harness stops
idempotency doing a request twice has the same effect as doing it once

Technique 1: workflow or agent?

Problem it solves: tells you whether you’re building an agent at all (slides 8 to 9).

The deciding question is control: does the model’s output choose the next step? A workflow can have tools, retrieval and memory too. The runtime in an agent still validates, executes and enforces limits.

Slide 9’s four systems.

System Answer Why
A. LLM labels each email as refund, complaint or other workflow one model call, fixed path
B. Docs chatbot: one search of the manual, then one answer workflow retrieval, but the program fixes the path
C. Coding assistant: edit, run tests, read failures, try again until pass or give up agent the model’s output picks the next step from what it just saw
D. Nightly: fetch sales, LLM summarises, email managers workflow tools, but a fixed pipeline

Quiz 1 asked the same thing: three LLM calls in a fixed order (summarise, classify urgency, draft) is a workflow, because it follows a predefined code path, even though it uses an LLM.

Technique 2: the agent loop

Problem it solves: maps the classical agent onto an LLM agent (slides 10 to 11).

The model generates \(u_t \sim p_\theta(\cdot \mid c_t)\): a distribution over generated output, not over successful actions. Even in an agent the model only generates text. A tool request is not, by itself, an action. So who acts? The harness.

Classical agent (Russell and Norvig) LLM-based agent
percepts via sensors feedback: tool results, errors, user replies
actions via actuators actions: tool calls, and the final answer
the agent program LLM call inside a loop, run by the harness

Technique 3: the harness’s six components

Problem it solves: a checklist of what an agent needs besides the model (slides 6 and 13, the lecture map).

Component Job in the airline clerk
LLM proposes the next search or fare check
Context builder decides what the model sees this step: task, schemas, filtered results
Control and dispatch validates calls, enforces permissions and limits (book_flight not exposed)
Tools search_flights, check_fare: how it observes and acts
Skills reusable procedure: how to compare fares and report caveats
State, memory and retrieval fare history, progress notes, the policy index
Planning and orchestration for bigger jobs (a five-city tour): plans, sub-agents

Technique 4: the loop, formally

Problem it solves: shows exactly which part is learned (slide 18).

\[c_t = \text{BuildContext}(m_t, g, T, K_t)\] \[u_t \sim p_\theta(\cdot \mid c_t)\] \[a_t = \text{InterpretAndValidate}(u_t)\] \[o_{t+1} = \text{Execute}(a_t)\] \[m_{t+1} = \text{UpdateState}(m_t, u_t, a_t, o_{t+1})\]

\(g\) = task, \(T\) = tool descriptions, \(K_t\) = skills loaded so far, \(m_t\) = runtime state. Only \(p_\theta\) is learned. Every other line is engineered: that’s the harness. In the role-play, the “Harness” player was BuildContext, InterpretAndValidate and UpdateState.

Cross-cutting harness duties: logging and traces, step and cost limits, retries and back-off, error handling, checkpoints.

Technique 5: from output to action, or not

Problem it solves: what happens to each kind of model output (slide 19).

  • Final answer → stop, return it to the user.
  • Question → ask the passenger, wait for the reply.
  • Tool request → validate: known tool? valid arguments? permitted? If yes, execute and record the result or error; if no, a rejection message.
  • Either way, update state and build the next context.

Two rules: errors and rejections are observations too (they go back into the context), and the runtime, not the model, owns validation, permissions, limits and termination.

Slide 17’s sample run. (1) search_flights(SFO, New York, 2027-04-18, after 10:00) → #293 10:00 $450, #441 12:00 $490 (the harness retried once after RateLimited). (2) check_fare(441) → $560: over budget. (3) search later departures → #517 14:30 $470, #602 18:45 $520. (4) check_fare(517) → $475, available. (5) Final answer: recommend #517 at $475; #293 fits only if “after 10:00” includes 10:00; nothing booked. Stop.

Notice: the searched price ($490) and the quoted price ($560) differ. Only the quote counts.

Technique 6: the minimal harness in code

Problem it solves: the loop is short enough to write in an exam (slide 20).

state = initialise(task)
for step in range(MAX_STEPS):
    context = build_context(state, tools, active_skills)
    output = call_model(context)            # the only learned line
    state.add(output)
    if output.is_final:
        return output.message
    if not output.tool_calls:
        state.add(feedback("expected tool call or answer"))
        continue
    for call in output.tool_calls:
        if not validate(call, tools):
            state.add(error(call, "invalid/not permitted"))
            continue
        try:
            result = execute(call)
        except ToolError as e:
            result = error(call, e)         # errors are observations
        state.add(call, result)
return "Stopped at step limit"

Which line is the only learned one? call_model(context). Real harnesses add permissions, context compaction, artefacts, checkpoints and sometimes sub-agents.

Technique 7: the failure autopsy

Problem it solves: diagnose which component failed, and what engineered fix catches it (slides 45 to 46).

Run What happened Component that failed Fix
1 step 2 search: #441 $490; step 3 quote: $560; context compacted at step 9; step 14: “Best option #441 at $490” state and context: compaction kept the old price and dropped the new one; nothing marked which was current reconciled working state that survives compaction
2 search_flights(date="18/04") → error “date must be YYYY-MM-DD”; same call 8 more times; “Stopped at step limit” model interpretation and control: model ignored the error; harness didn’t notice the repeats detect repeated identical failures; error messages that show a valid example
3 search, quote $475, then “Done, I’ve booked you on #517” (no booking tool existed) model output: claimed an action that never happened check final answers against the action log

Not exposing book_flight prevented the harm in run 3, but not the false claim.

Three distinctions to take away (slide 48): (1) model output ≠ environment action: the harness mediates every tool call. (2) context ≠ persistent, correct world state: the model sees a designed, possibly incomplete view. (3) LLM inference ≠ the whole agent policy: context building, tools, memory, control and stopping jointly shape behaviour.
