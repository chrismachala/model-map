Tools and skills

A tool is how an agent observes or changes the world. A skill is a folder of know-how it loads only when needed. And the rule "do not book yet" is safest not as a sentence the model must remember, but as something the harness enforces.

Kind: LLM-based agent.
Week: 6, Part III first half (slides 21 to 29).
Book: not in Wooldridge. Optional: Anthropic, Equipping agents for the real world with Agent Skills (2025); agentskills.io; the Model Context Protocol specification.
Techniques on this page: where a rule should live, how a model calls a tool, designing a safe write tool, agent skills and progressive disclosure, tools vs skills, wider action spaces and MCP.

The problem it solves

The clerk must not book yet. You could write that in four places, and they are not equally safe. The harness also has to tell the model which tools exist and how to call them, which is just more text in its context. And as agents take on more kinds of work, you can’t stuff every procedure into every prompt: that’s what skills are for.

Words you’ll hear

Word Plain meaning
tool a named callable interface with a schema; the model requests it, the harness executes it
tool schema name + description + parameter types, given to the model as text
read tool observes without changing anything (search_flights, check_fare)
write tool changes the world (book_flight), so needs stricter preconditions
skill a folder with SKILL.md (and optional scripts, references, assets) holding a reusable procedure
progressive disclosure only a skill’s name and one-line description sit in context until it’s needed
procedural memory knowing how to do things; skills store it outside the weights
MCP Model Context Protocol: a standard way for servers to expose tools with schemas to any compatible client
constrained decoding the API forces the output to match the schema; argument values still need checking

Technique 1: where should “do not book” live?

Problem it solves: puts a rule where it’s actually enforced (slide 22).

From weakest to strongest enforcement (and from least to most engineering):

Where How strong
A. system prompt: “Never book without approval” the model must remember and obey
B. a skill: the comparison procedure says “never imply a booking” loaded when relevant; still advisory
C. the book_flight tool description: “only call after explicit approval” close to the action; still advisory
D. the harness: a validation rule, or simply not exposing book_flight enforced regardless of what the model generates

Anything the model reads is a request to the model. Only the harness can guarantee.

Technique 2: how a model calls a tool

Problem it solves: gets from free text to an executed function (slide 23).

  1. The tool schema goes into the context as text: {"name": "check_fare", "description": "Current price...", "parameters": {"flight_id": "string"}}.
  2. The LLM generates tokens, e.g. {"name":"check_fare","arguments":{"flight_id":"441"}}.
  3. The harness parses and validates it, then calls check_fare("441").

The model “knows” a tool only by reading its description. Models are post-trained on tool-use formats so they usually emit valid requests, but parsing can still fail; constrained decoding forces the shape, but argument values must still be checked. Consequence: tool names and descriptions are prompt engineering. A vague description produces vague calls.

Technique 3: designing a safe write tool

Problem it solves: a booking tool that can’t book the wrong thing, at the wrong price, twice, or without permission (slide 24).

book_flight(
    quote_id: str,         # binds to a checked fare: right flight, right price
    passenger_id: str,
    approval_token: str,   # issued by the supervisor: no permission, no booking
    idempotency_key: str,  # a retry never books twice
) -> BookingConfirmation | Refused

Read tools observe; write tools change the world, so their preconditions are stricter. The approval token moves the supervisor’s role into the interface itself.

Which parameter stops which failure? Wrong flight or a stale price → quote_id (it names one specific checked quote). Booking twice after a RateLimited retry → idempotency_key. Booking without the passenger’s OK → approval_token. Booking for the wrong person → passenger_id.

Technique 4: agent skills and progressive disclosure

Problem it solves: many procedures available, few occupying the context (slides 25 to 27).

flight-comparison/
  SKILL.md
  scripts/rank_options.py
  references/fare_rules.md
  assets/report_template.md

SKILL.md starts with a header (name, description) then the procedure: filter by strict constraints; verify every price with check_fare; flag stale quotes and ambiguous constraints; never imply a booking.

Progressive disclosure, three levels:

  1. Discover: only the name and one-line description are in context (about a hundred tokens).
  2. Load: when relevant, the agent reads SKILL.md.
  3. Use: follow it; open references or run scripts only if needed.

Skills are procedural memory: knowing how, stored outside the weights.

The roll-dice skill (slide 26). Header: name: roll-dice, description: Roll dice using a random number generator. Use when asked to roll a die.... Body: run echo $((RANDOM % <sides> + 1)) (or the PowerShell equivalent). Note the skill contains a script, but running it still goes through an execution tool.

Technique 5: tools vs skills

Problem it solves: they are not synonyms (slide 28).

Tool Agent skill
purpose execute an operation or get data supply reusable know-how and procedures
form named callable interface + schema folder with SKILL.md, optional scripts and references
when used the model requests it; the harness executes the harness discovers and loads it on demand
example check_fare(flight_id) “how to compare fares and report caveats”

A skill teaches the agent how and when to use tools; a tool is how it observes or acts.

Technique 6: wider action spaces and MCP

Problem it solves: agents need more than narrow APIs (slide 29).

Capability What it enables
narrow API tool one well-defined function such as check_fare
code execution write and run small programs to transform data, compute, inspect files
computer use operate graphical interfaces by clicks, typing and screenshots
workspace / files create and inspect persistent artefacts across many steps

MCP lets servers expose named tools with schemas to any compatible client: it’s interoperability infrastructure, not an agent and not a model. Wider capabilities add flexibility; the harness must still handle results, failures and action boundaries.
