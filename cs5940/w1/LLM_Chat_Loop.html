Practical 1: the chat loop

Your first LLM program. The big surprise: the model remembers nothing between calls. Your program has to resend the whole conversation every time, and that is where memory, cost and context limits all come from.

Kind: practical (LLM code).
Week: 1 practical, Parts 1 to 4.
Book: none. The practical pages are the source.
Techniques on this page: the first request, the statelessness experiment, conversation history with roles, the system message, the interactive loop, the cost of a growing context.

The problem it solves

The practicals build an LLM-based agent from scratch, with no framework, so you can see and debug every part. Week 1 is the base layer: a chat loop.

The lesson that matters for the whole module: the LLM does not control your application; your code does. Your code decides what the model is sent, what it’s allowed to do, and what happens to its reply. Later practicals add tools, retrieval and decisions on top, but they all stand on this loop.

Words you’ll hear

Word Plain meaning
LLM a model that takes text in and generates text out
LLM server where the model runs; your program talks to it over the network
API the agreed format for requests (model, messages, settings) and responses
LiteLLM a Python library with one completion(...) call for many providers
openai/qwen3-14b “use the OpenAI request format” + “the Qwen3-14B model on the course server” (it is not an OpenAI model)
stateless each call starts from nothing; nothing is remembered between calls
token a small piece of text (roughly ¾ of a word); costs and limits are counted in tokens
role who a message is from: system, user or assistant
virtual environment (venv) a private folder of Python packages for one project

Technique 1: setup and the first request

Problem it solves: talk to the course model safely, without leaking your key.

source ~/.config/csx940/env     # sets OPENAI_BASE_URL and OPENAI_API_KEY
python -m venv .venv
source .venv/bin/activate
pip install litellm
import os
from litellm import completion

response = completion(
    model="openai/qwen3-14b",
    api_base=os.environ["OPENAI_BASE_URL"],   # where the server is
    api_key=os.environ["OPENAI_API_KEY"],     # the credential
    messages=[{"role": "user", "content": "What is the capital of France?"}],
)
print(response.choices[0].message.content)

Read the last line left to right: the list of generated choices (usually one), the first, its message, its text content. The response also carries usage (prompt, completion and total tokens).

  • Why a venv? It keeps this project’s packages apart from everything else, so installs don’t break each other.
  • Why not put the key in the code? Code gets shared, screenshotted and committed to Git. An environment variable keeps the secret out of the file.

Technique 2: the statelessness experiment

Problem it solves: shows you, by experiment, where memory does and doesn’t live.

  1. Send "My favourite module is CS3940."
  2. Change the message to "What is my favourite module?" and run again.

The model doesn’t know. The second request contained only the second message. It may say so, or guess (which is why you inspect rather than trust).

Key idea: the model can only use the context your application sends with the current request.

Web chat apps seem to remember because the app resends the conversation every time.

Technique 3: conversation history with roles

Problem it solves: gives the model a memory, by sending the whole conversation each time.

Role Written by Used for
system you, the developer instructions about behaviour (“You are a teaching assistant…”)
user the person their messages
assistant the model its earlier replies 
messages = []
messages.append({"role": "user", "content": "My favourite module is CS3940."})
response = completion(model=..., api_base=..., api_key=..., messages=messages)
answer = response.choices[0].message.content
messages.append({"role": "assistant", "content": answer})

Where is the memory? In the messages list. Not in the model, not in LiteLLM.

Why store the model’s replies too? Without them the model sees a user talking to nobody. It can’t resolve “what did you mean by that?”, repeats itself, and loses questions it asked (which the study-assistant challenge needs).

Technique 4: the system message

Problem it solves: sets behaviour for the whole session, separately from what the user types.

messages = [
    {"role": "system", "content": "You are a pirate. Answer every question like a pirate."},
    {"role": "user", "content": "Explain what a Python list is."},
]

Same question, different system message, different style. Try “one sentence”, “explain to a 10-year-old”, “at most 30 words”. The model usually complies but not always: instructions influence behaviour, they don’t guarantee it.

Study-assistant challenge: where should the topic the user picks go? Best in the system message (f"... The topic is {topic}."), because it should hold for the whole session and stays at the top of the context.

Technique 5: the interactive loop

Problem it solves: a real conversation, one turn after another.

messages = []
while True:
    user_message = input("You: ")
    if user_message.strip().lower() == "quit":
        break
    messages.append({"role": "user", "content": user_message})
    response = completion(model=..., api_base=..., api_key=..., messages=messages)
    answer = response.choices[0].message.content
    messages.append({"role": "assistant", "content": answer})
    print("Assistant:", answer)

get input → add to messages → send → receive → store → repeat. The practical’s version uses .lower() only; adding .strip() also catches " Quit ".

In the lecture’s terms: observation = what the user types; memory = the messages list (outside the model); objective = the system prompt; decision = model inference; learning = none; actions = printing text. No tools and no choice of control flow, so it is not yet an agent (see agent vs workflow).

Technique 6: the cost of a growing context

Problem it solves: explains why long chats get slow and expensive, and why week 2 trims the history.

Say the system prompt is \(s\) tokens, each user message \(u\) and each reply \(a\). Request \(t\) carries the system prompt, \(t\) user messages and \(t - 1\) replies:

\[\text{tokens sent at turn } t = s + t\,u + (t-1)\,a\]

Adding up \(T\) turns, with \(\sum_{t=1}^T t = \frac{T(T+1)}{2}\):

\[\text{total} = T s + u\,\frac{T(T+1)}{2} + a\,\frac{T(T-1)}{2}\]

That is quadratic in \(T\): double the conversation and the input tokens roughly quadruple.

Worked example. \(s = 50\), \(u = 20\), \(a = 80\), \(T = 10\).

  • Turn 1 sends \(50 + 20 + 0 = 70\) tokens; turn 10 sends \(50 + 200 + 720 = 970\).
  • Total: \(10 \times 50 + 20 \times 55 + 80 \times 45 = 500 + 1100 + 3600 = 5200\).

The practical’s rules, and why

  1. Use the LLM only through the interfaces provided.
  2. No unrestricted web access for the LLM.
  3. Never automatically run code the LLM wrote. Treat it as untrusted input.
  4. No secrets or personal data in prompts.
  5. Credentials outside source code.
  6. Inspect what the system does; a response is not automatically correct.

These limit what the agent can actually do (design dimension 6), which is the delegation problem handled in practice.
