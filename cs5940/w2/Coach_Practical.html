Practical 2: the running coach

Week 1's script grows into reusable parts for a running coach: one function for every model call, a token budget, a settings file, a user profile, and a conversation that forgets old messages on purpose.

Kind: practical (LLM code).
Week: 2 practical, Parts 1 to 4.
Book: none. The practical pages are the source.
Techniques on this page: call_llm, thinking models, the token budget (and its overshoot), config.toml, the user profile in the system prompt, the trimmed conversation window, save and resume.

The problem it solves

Week 1’s program worked, but every call was copy-pasted, costs grew without limit, and settings and secrets were mixed into the code. Week 2 turns it into an application you can control: one place where every model call goes through, a budget so a runaway loop can’t burn your hourly allowance, and state the application owns, including the decision about what to forget.

Key idea: state belongs to the application, including the decision about what to forget.

Words you’ll hear

Word Plain meaning
token a small piece of text (about ¾ of a word); costs and limits are counted in these
context window the most tokens one request can hold, every message included
temperature randomness: near 0, the model almost always picks its most likely next word
thinking / reasoning model writes out reasoning before answering: better on multi-step problems, more tokens, slower
extra_body passes a server-specific setting through LiteLLM unchanged
TOML a settings-file format that, unlike JSON, allows comments
type hints messages: list[dict]: documentation Python doesn’t enforce
max_messages (\(k\)) how many recent history messages are sent each turn

Technique 1: one function for every model call

Problem it solves: change the model, count tokens or enforce a budget once, not everywhere.

MODEL = "openai/qwen3-14b"

def call_llm(messages: list[dict], temperature: float = 0.2) -> tuple[str, Any]:
    """Send messages to the model and return (reply_text, usage)."""
    response = completion(model=MODEL, api_base=os.environ["OPENAI_BASE_URL"],
                          api_key=os.environ["OPENAI_API_KEY"],
                          messages=messages, temperature=temperature)
    text = response.choices[0].message.content or ""
    return text, response.usage

The or "" guards against content being None. The coach uses temperature 0.2 for consistent advice.

Technique 2: thinking, and keeping it out of the history

Problem it solves: use extra reasoning only when it’s worth the cost.

Qwen3 is hybrid: thinking is off by default on the course server and switched on per request:

extra_body={"chat_template_kwargs": {"enable_thinking": thinking}}
reasoning = getattr(message, "reasoning_content", None)   # None if there isn't any

For “Hello!” thinking is wasted; for “Is 20 km a week enough for a 10 km race?” it helps.

Why not store the reasoning in the history? It’s often far longer than the answer, and the whole history is resent every turn, so it would multiply the cost of every later call. call_llm returns only message.content, and .strip() removes the blank lines left behind.

Technique 3: the token budget

Problem it solves: stops a bug from spending the course allowance (700,000 tokens per hour, 2,000,000 per day).

TOKENS_USED = 0
TOKEN_BUDGET = 100_000

class TokenBudgetExceeded(Exception): ...

def call_llm(...):
    global TOKENS_USED
    if TOKENS_USED >= TOKEN_BUDGET:
        raise TokenBudgetExceeded(f"This run has used its budget of {TOKEN_BUDGET} tokens.")
    response = completion(...)
    TOKENS_USED += response.usage.total_tokens

The overshoot. The check happens before each call, using the total so far. If every call uses \(c\) tokens and the budget is \(B\):

\[\text{calls made} = \left\lceil \frac{B}{c} \right\rceil, \qquad \text{tokens used} = c\left\lceil \frac{B}{c} \right\rceil < B + c.\]

A run can overshoot by less than one call’s worth.

Worked example. \(B = 10{,}000\), \(c = 4{,}000\). Before call 1 the total is 0, before call 2 it’s 4,000, before call 3 it’s 8,000: all below 10,000, so 3 calls run (\(\lceil 2.5 \rceil = 3\)), using 12,000 tokens. The 4th call raises TokenBudgetExceeded.

With \(B = 100{,}000\) and \(c = 3{,}000\): \(\lceil 33.3 \rceil = 34\) calls, 102,000 tokens, an overshoot of 2,000.

Technique 4: settings in config.toml

Problem it solves: change settings without editing code, and record which settings gave a result.

# config.toml. Secrets (API key, server URL) stay in environment variables.
[model]
name = "openai/qwen3-14b"
temperature = 0.2
thinking = false
token_budget = 100_000   # per script run
CONFIG_FILE = Path(__file__).with_name("config.toml")   # next to config.py, wherever you run from
CONFIG = tomllib.loads(CONFIG_FILE.read_text(encoding="utf-8"))

What goes where: values you change between runs (model, temperature, thinking, budget) go in config.toml; secrets never do (environment variables); logic stays in code. The file is read once, at import, so restart Python after editing it.

Technique 5: the user profile

Problem it solves: makes advice specific to the runner, by putting facts in the system prompt.

def build_system_prompt(profile: dict) -> str:
    return f"""You are a supportive running coach.
Give short, practical advice (at most 5 sentences).

Athlete profile:
{json.dumps(profile, indent=2)}
"""

Who decides what the model sees? The application. Changing current_weekly_km from 25 to 5 should change the advice. Changing race_date tells you little, because the model doesn’t know today’s date unless you put it in the prompt too.

In lecture terms the profile is explicit, inspectable state, a bit like a deductive agent’s \(\Delta\). But the LLM doesn’t reason soundly over it: it can still contradict the profile, so inspect the output.

Technique 6: the trimmed conversation window

Problem it solves: keeps each request’s cost bounded, at the price of forgetting.

class Conversation:
    def __init__(self, system_prompt: str, max_messages: int = 10) -> None:
        self.system_prompt = system_prompt
        self.max_messages = max_messages
        self.history: list[dict] = []

    def get_messages(self) -> list[dict]:
        recent = self.history[-self.max_messages:]
        return [{"role": "system", "content": self.system_prompt}] + recent

Why is the system prompt outside the window? It holds the role, the rules and the profile. If it were trimmed the coach would turn into a generic assistant after a few turns.

The maths. At turn \(t\) (after add_user) the history holds \(2t - 1\) messages. The turn-1 message is still sent iff

\[2t - 1 \le k \iff t \le \frac{k + 1}{2}.\]

Worked example. \(k = 4\): turn 1’s message is sent at turns 1 and 2 only (\(t \le 2.5\)). From turn 3 it’s gone, so at turn 6 the coach can’t know your shoe size. The model didn’t “forget”: your application chose not to send it.

\(k = 6\): sent up to turn 3. Default \(k = 10\): up to turn 5.

At turn 3 with \(k = 4\), get_messages() returns 5 messages: the system message plus the last 4 of the history’s 5.

Without trimming, the prompt grows every turn (quadratic total, as in week 1). With a window it grows until the window is full, then stays roughly flat at about \(s + k\bar m\) tokens.

Save and resume: load session.json at start-up if it exists, and conv.save(SESSION_FILE) before break. The system prompt isn’t saved, because it’s rebuilt from the current profile each run.
