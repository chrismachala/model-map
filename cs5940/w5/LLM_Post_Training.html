Post-training and the three knobs

A pretrained model predicts web text. Post-training (fine-tuning on examples, then RL from preferences or from checkable answers) turns it into an assistant. And a quiz favourite: knowing which actions actually change the weights, and why a model that generates text still isn't an agent.

Kind: learning (how LLM behaviour is shaped after pretraining).
Week: 5, Part B, second half (slides 39 to 54).
Book: not in Wooldridge. Optional: Ouyang et al. 2022 (InstructGPT, RLHF), DeepSeek-AI 2025 (R1).
Techniques on this page: supervised fine-tuning, RLHF and RLAIF, RLVR, DPO, the DeepSeek-R1 case study, “reasoning” models as a continuum, the three knobs (training, decoding, inference-time compute), two meanings of “policy”, why an LLM is not yet an agent.

The problem it solves

Pretraining gives broad ability but no guarantee of truthfulness, of following instructions, or of pursuing goals reliably (slide 40). Post-training reshapes behaviour with new training signals. Some of it is RL, which is where Part A and Part B meet: the LLM becomes a policy \(\pi_\theta\) over tokens, and a reward pushes its probabilities.

Then the agent question (slides 50 to 53): even a well-trained model only generates tokens. To act in the world it needs something around it that executes requests, observes results and loops. That’s week 6.

Words you’ll hear

Word Plain meaning
SFT supervised fine-tuning: train on chosen (prompt, good response) pairs
RLHF RL from human feedback: humans compare responses → train a reward model → RL (e.g. PPO) towards higher reward
RLAIF the same, but an AI gives the preference judgements (e.g. Constitutional AI)
RLVR RL with verifiable rewards: a checker (right number, tests pass) gives the reward
reward model a network trained to score responses the way the human comparisons did
DPO direct preference optimisation: learn straight from chosen/rejected pairs; no separate reward model, no RL loop
GRPO group relative policy optimisation: PPO-style, scores each answer against other answers to the same question; no critic
in-context examples worked examples put in the prompt; change the output but not the weights
reward hacking / overoptimisation getting high reward without the behaviour you wanted
inference-time compute spending more computation at answer time: reasoning tokens, several attempts, search, checking

Technique 1: the post-training menu

Problem it solves: different signals teach different things (slide 42).

Stage / method Training signal Main idea
pretraining next token in a text corpus general ability and representations
SFT target responses to prompts task behaviour and formatting
RLHF human comparisons → reward model RL towards preferred responses
RLAIF AI-generated preference judgements RL with AI-derived feedback
RLVR automatically checked answers or outcomes RL for verifiable success

Not a fixed recipe: stages can be mixed, repeated or skipped. DPO learns from chosen/rejected pairs without a reward model or RL loop.

SFT (slide 43) trains on demonstrations (“Explain Q-learning simply” → a clear explanation). It updates the weights. Putting examples in the prompt does not. Standard SFT doesn’t compare good and bad answers; preference methods do.

RLHF pipeline (slide 44): prompt → policy \(\pi_\theta\) writes candidate responses → humans (or an AI, for RLAIF) compare them → a reward model learns those preferences → RL update of the policy against the reward model. Risk: the policy finds ways to score highly that the reward model mis-rates (overoptimisation, reward hacking again).

RLVR (slide 45): maths or code problem → model writes a solution → a verifier checks the answer or runs tests → reward → RL update. Less subjective than human judgement, but incomplete tests can still be gamed. Typically the whole completed response gets one outcome reward.

Which method? (a) A team has 10,000 expert-written answers to customer questions: SFT. (b) Labellers say which of two answers is better, and a model is trained to predict their choice, then used as the reward: RLHF. (c) Each answer to a maths problem is marked right or wrong by comparing with the known result: RLVR. (d) Pairs of (preferred, rejected) responses, trained on directly with no reward model: DPO.

Technique 2: DeepSeek-R1, the RL case study

Problem it solves: shows RL can improve reasoning in an already-pretrained model (slide 46).

DeepSeek-R1-Zero DeepSeek-R1
starts from DeepSeek-V3-Base DeepSeek-V3-Base
post-training RL (GRPO) only, no SFT first cold-start SFT → reasoning RL → curated SFT → final RL
feedback mainly rule-based accuracy and format rewards rule-based, later also preference-based
what happened reflection and self-checking emerged strong reasoning, more readable, more useful

R1-Zero’s catch: poor readability and language mixing, which R1’s extra SFT and RL fixed.

“Reasoning” vs “standard” models are a continuum (slide 47): they differ in training (extra reasoning SFT/RL, verifiable rewards), in inference compute (more tokens, attempts, search), in system setup (adjustable effort, routing), and in what’s shown (a summary is not necessarily the whole internal process). More compute at answer time can help hard tasks but doesn’t guarantee correctness.

Technique 3: the three knobs

Problem it solves: three different things all get called “making the model better” (slide 48).

Knob What it does Changes \(\theta\)?
1. Training pretraining, SFT, preference optimisation, RL yes
2. Decoding how tokens are picked: greedy, temperature sampling no
3. Inference-time computation extra reasoning steps, samples or checking before the final answer no

If a model solves a hard question after “thinking longer”, has it learned? No: it computed more or used more context. Learning means a training update to \(\theta\).

Poll 3 (slide 49): which updates θ? Only training with verifiable rewards (RLVR) (D). Lower temperature (A) is decoding; worked examples in the prompt (B) are context; more reasoning tokens (C) are inference-time compute. None of those touches the weights. This is a likely quiz trap: “in-context learning” sounds like learning but isn’t a weight update.

Technique 4: two meanings of “policy”

Problem it solves: the word is used for the model and for the agent, and they’re different (slide 50).

Model-level policy Agent-level policy
\(\pi_\theta(x_t \mid c, x_{<t})\) \(\pi(a_t \mid h_t, g)\)
a distribution over next tokens, given context and earlier tokens a choice of environment actions, given the interaction history and the goal

An LLM can implement part of an agent policy, e.g. by writing a structured tool request. But a token distribution is not an executed policy over tools or physical actions: an executor has to interpret and run the request. And a frozen model can still respond differently as its context changes, without learning anything.

Technique 5: an LLM is not yet a tool-using agent

Problem it solves: separates “says it will act” from “acts” (slide 51).

The loop an agent needs: context → frozen LLM → reply or a proposed tool request → controller and executor (with permissions) runs it → tool results go back into the context and memory → next step. Tool calling needs an executor and permissions, not just tool-shaped text.

The five distinctions (slide 53), worth learning word for word:

  1. Q-table vs DQN: tabular values vs neural function approximation.
  2. Model-free vs model-based: learning without a dynamics model vs using one to plan or learn.
  3. RL vs pretraining: optimising reward vs predicting tokens in training data.
  4. Training vs inference: updating parameters vs generating with (normally) fixed parameters.
  5. LLM vs LLM agent: token generation vs a runtime action–observation loop with tools and control logic.
